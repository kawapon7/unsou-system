# 案件一括インポート＋案件カテゴリ列 設計書

作成日: 2026-08-25 / 更新: 2026-08-25（カテゴリ列を追加）/ 対象: HIBIKI（運送業SaaS）/ 状態: 設計確定・実装前

## 1. 目的と背景

新規導入先の**案件（`projects`）をExcelから一括登録**する。取引先一括インポート（2026-08-24 リリース済み）と同じ画面・同じ操作感で完結させる。

あわせて、**案件に区分（カテゴリ）列を持たせ、帳票の判定を案件名の文字列マッチから切り離す**。

### 動機

1. **初期投入の省力化**。案件を画面から1件ずつ登録すると件数分の手作業になる。
2. **案件名の統一**。導入先が使っている案件名を一覧化してから登録し、表記の揺れた案件が乱立するのを最初の時点で防ぐ。
3. **案件名を「ただの表示名」にする**。現状、おおば様式の帳票は案件名に `作業`・`デバンニング`・`荷役` のいずれかが含まれるかで作業系案件を判定している（`web/src/utils/ooba-invoice-lines.ts` の `isWorkTypeProject`）。この判定結果は支払通知書の**明細の並び順**と**「※人員結果は別紙参照」の出し分け**を決めている（金額そのものは変わらない）。名前を変えただけで帳票の見た目が変わる状態は、取引先の社名変更・案件名の整理を妨げる。

システムのデータ連結はUUID（`projects.client_id` → `clients.id` など）で行われているため、社名や案件名の変更自体は本来自由に行える。**唯一の例外がこの文字列判定**であり、ここを直せば案件名は純粋な表示名になる。

導入先ごとの命名ルールは規定しない。**顧客が現に使っている呼び方をそのまま受け入れる**（汎用性を優先）。

## 2. スコープ

### 含む

- `projects` に区分（カテゴリ）列を追加し、帳票の判定を置き換える
- 既存のインポート画面（`/admin/ops/import`）のテンプレートに「案件」シートを追加
- 案件行の検証・変換（純関数）と登録処理
- 案件コードの自動採番
- 案件登録画面（`/admin/projects`）への区分の入力欄追加
- `partner-import.ts` に混入しているNUL文字の解消（下記）

### 含まない

- 案件コードへの意味付け（会社コード体系の導入）。案件コードは人が読むラベルであり、データの同一性はUUIDが担保している。実務で案件コードに触れる場面が少ないため、`P0001` 形式の自動採番で足りる。会社コード体系が必要になったら、採番ルールの差し替えだけで対応できる
- 画面から手入力する案件名の表記ゆれチェック（今回のインポートに閉じる）
- 既存案件の一括更新・リネーム（本番の `projects` は0件。重複はエラーで弾く）
- 発着地・単位種別・利益率の入力（案件登録画面自体が設定していない項目のため、テンプレに含めない）
- 人員結果表（別紙）の実装（従来どおり対象外）

### 付随して直すもの: NUL文字によるgit差分の不可視化

`web/src/utils/partner-import.ts` の `departmentKey` は区切り文字に**リテラルのNUL文字**を埋め込んでいる。このためファイルがバイナリ扱いになり（`file` コマンドの判定が `data`、`git diff --stat` の表示が `Bin 0 -> 16667 bytes`）、**gitの差分が一切表示されない**。

実害は2つ。

1. このファイルの変更をレビューできない。今回まさにこのファイルへ案件の検証ロジックを追加する。
2. **コミット前のシークレット漏れスキャンが素通りする。** `docs/HANDOVER_MASTER.md` §2-6S の手順は `git diff --cached | grep -E "SERVICE_ROLE_KEY|..."` でチェックするが、バイナリ扱いのファイルは差分が出力されないため検査対象から実質外れる。

対処: リテラルのNUL文字を、同じ値を表すエスケープ表記（バックスラッシュ＋`u0000`）に置き換える。実行時の値は同一（テストで担保）で、ファイルはプレーンテキストに戻り、差分もスキャンも効くようになる。

## 3. 案件カテゴリ列

### 列定義

`projects` に次の列を追加する（マイグレーション）。

| 項目 | 内容 |
|---|---|
| 列名 | `category` |
| 型 | `text` NOT NULL |
| 既定値 | `'transport'` |
| 制約 | `check (category in ('transport','work'))` |

値の意味は `transport` = 輸送系（配送・横持ち等）、`work` = 作業系（デバンニング・荷役等）。2値に絞るのは、現在の判定が2分岐だから。将来分類を増やす場合は制約の値を足す。

### 既存データの移行

マイグレーション内で、既存行を現行ルールと同じ基準でバックフィルする。

```sql
update projects
set category = 'work'
where project_name like '%作業%'
   or project_name like '%デバンニング%'
   or project_name like '%荷役%';
```

これにより、移行前後で帳票の出力は変わらない（本番の `projects` は0件だが、テスト環境のデモデータで挙動を確認できる）。

### 帳票判定の置き換え

`isWorkTypeProject(name: string)` を廃止し、案件の `category` を見る形にする。

呼び出し元は `web/src/app/_actions/pdf-actions.ts` の1か所のみ（明細行の組み立て）。ここは既に `project_id` を持ち、案件名のマップ（`projMap`）を作っているため、そのマップに `category` を含める形に拡張する。

`project_id` が無い行（突発案件・マスタ外の記録）は `transport` 扱いとする。現行も案件名が `（案件なし）` となり作業系語を含まないため `false` になっており、**挙動は変わらない**。

`WORK_TYPE_WORDS` の定義と `isWorkTypeProject` は削除する。既存テスト（`ooba-invoice-lines.test.ts`）の該当ケースは、カテゴリ値による判定のテストに置き換える。

### 手入力経路

案件登録画面（`/admin/projects`）のフォームに区分の選択（輸送系／作業系）を追加する。インポートだけで設定できてもマスタ運用が片手落ちになるため。既定は輸送系。

### 適用順序（重要）

**マイグレーション適用 → デプロイ** の順を厳守する。逆にすると `category` 列が存在しない状態で新コードが動き、帳票生成が失敗する。様式②のときと同じ手順（`docs/HANDOVER_MASTER.md` §5-2 参照）。

## 4. テンプレート仕様

既存テンプレートに4枚目のシート **「案件」** を追加する。シート構成は `請求先 / 部署 / 委託先 / 案件`。

### 列

| 列名 | 必須 | 内容 |
|---|---|---|
| 荷主 | 必須 | 請求先シートの会社名、または既存DBの請求先名と一致すること |
| 部署 | 条件付き必須 | 荷主が「部署を使う＝あり」の場合のみ必須。「なし」の場合は空欄 |
| 案件名 | 必須 | 導入先の呼び方をそのまま |
| 区分 | 必須 | `輸送系` または `作業系` |
| 委託先 | 任意 | 委託先シートの名前、または既存DBの委託先名と一致すること |
| 売上単価 | 必須 | 0以上の整数 |
| 仕入単価 | 任意 | 0以上の整数。空欄は未設定（NULL） |

区分を**必須**にするのは、空欄を既定値で埋めると誤分類に気づけないため。記入者に明示的に選ばせる。記入例とガイド行で選択肢を示す。

案件コードは列に含めない（§6で自動採番）。

### 行構成

既存3シートと同じ。1行目＝列名、2行目＝必須/任意ガイド（`※`始まり）、3行目＝記入例（`例）`始まり）、4行目以降がデータ。ガイド行と記入例行は残したまま取り込んでも無視される。

### 後方互換

**案件シートが存在しないファイルもエラーにしない。** 取引先インポート時代のテンプレートで記入済みのファイルが投入される可能性があるため、案件シートが無い場合は空として扱う。逆に、請求先・部署・委託先シートを空にして案件シートだけ記入したファイルも有効とする（取引先を登録済みの導入先に、後から案件だけ追加する用途）。

## 5. 検証ルール

すべての検証は既存の `validateAndConvert`（`web/src/utils/partner-import.ts`）に追加する。**1件でもエラーがあれば1件も登録しない**（全件中止）。エラーはシート名・Excel行番号・列名・理由の4点セットで全件収集する。

### 5-1. 必須・形式

| 項目 | ルール | エラー文言（例） |
|---|---|---|
| 荷主 | 空欄不可 | 必須項目です |
| 案件名 | 空欄不可 | 必須項目です |
| 区分 | 空欄不可・`輸送系`/`作業系` のいずれか | 「輸送系」「作業系」のいずれかで入力してください |
| 売上単価 | 空欄不可・0以上の整数 | 0以上の整数で入力してください |
| 仕入単価 | 空欄可・書けば0以上の整数 | 0以上の整数で入力してください |

数値は、全角数字とカンマ区切り（`1,000`）を正規化してから判定する。それ以外の文字が混ざる場合はエラー。

### 5-2. 参照の解決

荷主・部署・委託先は、**同一ファイル内の該当シート、または既存DB**のいずれかに存在すれば通る。どちらにも無ければエラー（`請求先シートにも既存データにも見つかりません`）。

### 5-3. 部署の要否

荷主の `use_departments` により分岐する。判定材料は、同一ファイルの請求先シートの「部署を使う」列、または既存DBの `clients.use_departments`。

- 「あり」の荷主 → 部署が空欄ならエラー
- 「なし」の荷主 → 部署が記入されていればエラー（`この荷主は部署を使わない設定です`）

「なし」なのに部署が書かれた行を黙って無視すると、記入者は登録されたつもりで実際は反映されていない状態になるため、明示的にエラーとする。

### 5-4. 重複

同一性のキーは **(荷主・部署・案件名)** の3点。部署が異なれば同名の案件（例:「定期便」）が並存しうるため、部署をキーに含める。部署が空欄の行は、キー上「部署なし」という1つの値として扱う（同じ荷主・同じ案件名で部署なしの行が2つあれば重複エラー）。キーの区切りには通常の文字列に現れないNUL文字を使い、名前に区切り文字が含まれても衝突しないようにする（既存の `departmentKey` と同じ方式。ただしソース上はエスケープ表記で書く）。

- ファイル内での重複 → エラー
- 既存DBとの重複 → エラー（`既に登録されている案件です`）

### 5-5. 表記ゆれの扱い

重複判定の比較時のみ、案件名を次の順で正規化する。

1. Unicode NFKC 正規化（全角英数字・全角記号を半角へ）
2. 空白文字をすべて除去（半角スペース・全角スペース・タブ）
3. 英字を小文字化

**保存する案件名はExcelに書かれた文字列そのまま**とする。システムが名前を書き換えることはしない（帳票に出る名前が提出内容と食い違うのを避けるため）。正規化は「実質同じ名前」を検出してエラーにするためだけに使う。

荷主名・部署名・委託先名の照合は、既存の請求先・委託先の照合と揃えて**完全一致**とする（ここを緩めると、別の取引先に誤って紐づく事故の可能性があるため）。

## 6. 案件コードの自動採番

`projects.project_code` は `P` + 4桁ゼロ埋め連番（`P0001`）とする。

- インポート時、テナント内の既存 `project_code` のうち `^P\d+$` に一致するものの最大値を求め、その次の番号から連番を振る
- 4桁で足りなくなった場合は桁が増える（`P10000`）
- 突発案件の昇格が生成する `SP-YYYYMMDD-XXXXX` 形式（`web/src/app/_actions/project-actions.ts`）とは接頭辞が異なるため衝突しない
- `project_code` にDBの一意制約は無い。採番は登録処理内で行い、同一インポート内での重複は連番により発生しない

## 7. 登録処理

`importPartners`（`web/src/app/_actions/partnerImportActions.ts`）に案件の登録を追加する。運営者ゲート（`requireOperator`）はそのまま適用される。

### 実行順

**請求先 → 部署 → 委託先 → 案件**。案件は前段で登録した結果のIDマップ（名前→ID）を使って `client_id` / `department_id` / `contractor_id` を解決する。既存DBに登録済みの取引先も同じマップに含める。

### 既定値

| 列 | 値 |
|---|---|
| `unit_type` | `'quantity'` |
| `status` | `'accepted'` |
| `driver_visible` | `true` |
| `default_margin_rate` | DB既定値（10.00）に委ねる |
| `category` | Excelの「区分」列から（必須のため既定値に頼らない） |

### 挿入経路

案件の挿入は既存の `createProject`（`web/src/app/admin/projects/actions.ts`）を経由する。`tenant_id` の付与をそちらが行っているため、ここでDBに直接挿入しない（取引先側で口座の暗号化を既存アクションに委ねているのと同じ方針）。

## 8. エラー処理

### 検証エラー

1件も登録せず、既存のエラー表（シート・行・列・理由）に案件シートの行も混ぜて表示する。

### 挿入中のエラー

Supabase の Server Action ではトランザクションを張れないため、挿入途中の失敗は既存の `partialFailure` と同じ扱いとする。「ここまでに登録した件数（請求先◯件・部署◯件・委託先◯件・案件◯件）」を表示し、残りだけのファイルで再実行するよう案内する。再実行時は重複検査が防波堤になる。

## 9. テスト方針

### 単体テスト（`web/src/utils/partner-import.test.ts` に追加）

- 正常系: 案件行が変換され、名前・区分・単価・既定値が期待どおり
- 必須欠落: 荷主・案件名・区分・売上単価それぞれの空欄
- 区分: 「輸送系」「作業系」以外の値でエラー
- 数値: 全角数字・カンマ区切りの許容、負数・文字混入のエラー
- 参照解決: ファイル内の請求先で解決／既存DBの請求先で解決／どちらにも無い
- 部署の要否: 「あり」で空欄→エラー、「なし」で記入→エラー、「あり」で正しく記入→通る
- 重複: ファイル内重複、既存DB重複、部署違いの同名は通る
- 表記ゆれ: 全角空白・半角空白・全角英数字の違いが重複として検出される
- 採番: 既存最大値の次から連番、既存ゼロなら `P0001`
- ガイド行・記入例行のスキップ
- 後方互換: 案件シートが無いファイル、案件シートだけのファイル
- `departmentKey` がエスケープ表記に変えても同じ値を返す

### 帳票テスト（`web/src/utils/ooba-invoice-lines.test.ts` の更新）

- カテゴリ `work` の案件が作業系ブロックに並び、`※人員結果は別紙参照` が出る
- カテゴリ `transport` の案件は非作業系ブロックに並ぶ
- 案件名に「作業」を含んでもカテゴリが `transport` なら非作業系として扱われる（文字列依存が切れたことの確認）

### 画面確認

ローカルの dev サーバーで、テンプレDL → 記入 → プレビュー（件数表示） → 投入 → 再投入（重複で全件中止）を実測する。投入後はDBで `project_code` の採番・`category`・各IDの紐づきを確認する。案件登録画面での区分の選択と保存も確認する。
