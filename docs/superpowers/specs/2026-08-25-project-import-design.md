# 案件一括インポート 設計書

作成日: 2026-08-25 / 対象: HIBIKI（運送業SaaS）/ 状態: 設計確定・実装前

## 1. 目的と背景

新規導入先の**案件（`projects`）をExcelから一括登録**する。取引先一括インポート（2026-08-24 リリース済み）と同じ画面・同じ操作感で完結させる。

動機は2つ。

1. **案件名の統一**。導入先が使っている案件名を一覧化してから登録することで、表記の揺れた案件が乱立するのを最初の時点で防ぐ。
2. **初期投入の省力化**。案件は画面から1件ずつ登録すると件数分の手作業になる。

**案件名の統一は帳票の正確性に直結する。** おおば運送様式の支払通知書は「作業系かどうか」を案件名の文字列で判定しているため（`docs/HANDOVER_MASTER.md` §5-2 の既知の制限。次版で `projects` のカテゴリ列化を予定）、案件名が揺れると金額計算が狂いうる。

導入先ごとの命名ルールは規定しない。**顧客が現に使っている呼び方をそのまま受け入れる**方針とする（汎用性を優先）。

## 2. スコープ

### 含む

- 既存のインポート画面（`/admin/ops/import`）のテンプレートに「案件」シートを追加
- 案件行の検証・変換（純関数）
- 案件の登録処理（既存 Server Action への追加）
- 案件コードの自動採番
- **`partner-import.ts` に混入しているNUL文字の解消**（下記）

### 付随して直すもの: NUL文字によるgit差分の不可視化

`web/src/utils/partner-import.ts` の `departmentKey` は区切り文字に**リテラルのNUL文字**を埋め込んでいる。このためファイルがバイナリ扱いになり（`file` コマンドの判定が `data`、`git diff --stat` の表示が `Bin 0 -> 16667 bytes`）、**gitの差分が一切表示されない**。

実害は2つ。

1. このファイルの変更をレビューできない。今回まさにこのファイルへ案件の検証ロジックを追加する。
2. **コミット前のシークレット漏れスキャンが素通りする。** `docs/HANDOVER_MASTER.md` §2-6S の手順は `git diff --cached | grep -E "SERVICE_ROLE_KEY|..."` でチェックするが、バイナリ扱いのファイルは差分が出力されないため検査対象から実質外れる。

対処: リテラルのNUL文字を、同じ値を表すエスケープ表記（バックスラッシュ＋`u0000`）に置き換える。実行時の値は同一（テストで担保）で、ファイルはプレーンテキストに戻り、差分もスキャンも効くようになる。

### 含まない

- 画面から手入力する案件の表記ゆれチェック（今回のインポートに閉じる）
- 既存案件の一括更新・リネーム（本番の `projects` は0件のため不要。重複はエラーで弾く）
- 案件のカテゴリ列化（別タスク）
- 発着地・単位種別・利益率の入力（案件登録画面自体が設定していない項目のため、テンプレに含めない）

## 3. テンプレート仕様

既存テンプレートに4枚目のシート **「案件」** を追加する。シート構成は `請求先 / 部署 / 委託先 / 案件`。

### 列

| 列名 | 必須 | 内容 |
|---|---|---|
| 荷主 | 必須 | 請求先シートの会社名、または既存DBの請求先名と一致すること |
| 部署 | 条件付き必須 | 荷主が「部署を使う＝あり」の場合のみ必須。「なし」の場合は空欄 |
| 案件名 | 必須 | 導入先の呼び方をそのまま |
| 委託先 | 任意 | 委託先シートの名前、または既存DBの委託先名と一致すること |
| 売上単価 | 必須 | 0以上の整数 |
| 仕入単価 | 任意 | 0以上の整数。空欄は未設定（NULL） |

案件コードは列に含めない（§5で自動採番）。

### 行構成

既存3シートと同じ。1行目＝列名、2行目＝必須/任意ガイド（`※`始まり）、3行目＝記入例（`例）`始まり）、4行目以降がデータ。ガイド行と記入例行は残したまま取り込んでも無視される。

### 後方互換

**案件シートが存在しないファイルもエラーにしない。** 取引先インポート時代のテンプレートで記入済みのファイルが投入される可能性があるため、案件シートが無い場合は空として扱う。逆に、請求先・部署・委託先シートを空にして案件シートだけ記入したファイルも有効とする（取引先を登録済みの導入先に、後から案件だけ追加する用途）。

## 4. 検証ルール

すべての検証は既存の `validateAndConvert`（`web/src/utils/partner-import.ts`）に追加する。**1件でもエラーがあれば1件も登録しない**（全件中止）。エラーはシート名・Excel行番号・列名・理由の4点セットで全件収集する。

### 4-1. 必須・形式

| 項目 | ルール | エラー文言（例） |
|---|---|---|
| 荷主 | 空欄不可 | 必須項目です |
| 案件名 | 空欄不可 | 必須項目です |
| 売上単価 | 空欄不可・0以上の整数 | 0以上の整数で入力してください |
| 仕入単価 | 空欄可・書けば0以上の整数 | 0以上の整数で入力してください |

数値は、全角数字とカンマ区切り（`1,000`）を正規化してから判定する。それ以外の文字が混ざる場合はエラー。

### 4-2. 参照の解決

荷主・部署・委託先は、**同一ファイル内の該当シート、または既存DB**のいずれかに存在すれば通る。どちらにも無ければエラー（`請求先シートにも既存データにも見つかりません`）。

### 4-3. 部署の要否

荷主の `use_departments` により分岐する。判定材料は、同一ファイルの請求先シートの「部署を使う」列、または既存DBの `clients.use_departments`。

- 「あり」の荷主 → 部署が空欄ならエラー
- 「なし」の荷主 → 部署が記入されていればエラー（`この荷主は部署を使わない設定です`）

「なし」なのに部署が書かれた行を黙って無視すると、記入者は登録されたつもりで実際は反映されていない状態になるため、明示的にエラーとする。

### 4-4. 重複

同一性のキーは **(荷主・部署・案件名)** の3点。部署が異なれば同名の案件（例:「定期便」）が並存しうるため、部署をキーに含める。部署が空欄の行は、キー上「部署なし」という1つの値として扱う（同じ荷主・同じ案件名で部署なしの行が2つあれば重複エラー）。キーの区切りには通常の文字列に現れないNUL文字を使い、名前に区切り文字が含まれても衝突しないようにする（既存の `departmentKey` と同じ方式）。

- ファイル内での重複 → エラー
- 既存DBとの重複 → エラー（`既に登録されている案件です`）

### 4-5. 表記ゆれの扱い

重複判定の比較時のみ、案件名を次の順で正規化する。

1. Unicode NFKC 正規化（全角英数字・全角記号を半角へ）
2. 空白文字をすべて除去（半角スペース・全角スペース・タブ）
3. 英字を小文字化

**保存する案件名はExcelに書かれた文字列そのまま**とする。システムが名前を書き換えることはしない（帳票に出る名前が提出内容と食い違うのを避けるため）。正規化は「実質同じ名前」を検出してエラーにするためだけに使う。

荷主名・部署名・委託先名の照合は、既存の請求先・委託先の照合と揃えて**完全一致**とする（ここを緩めると、別の取引先に誤って紐づく事故の可能性があるため）。

## 5. 案件コードの自動採番

`projects.project_code` は `P` + 4桁ゼロ埋め連番（`P0001`）とする。

- インポート時、テナント内の既存 `project_code` のうち `^P\d+$` に一致するものの最大値を求め、その次の番号から連番を振る
- 4桁で足りなくなった場合は桁が増える（`P10000`）
- `project_code` にDBの一意制約は無い。採番は登録処理内で行い、同一インポート内での重複は連番により発生しない

## 6. 登録処理

`importPartners`（`web/src/app/_actions/partnerImportActions.ts`）に案件の登録を追加する。運営者ゲート（`requireOperator`）はそのまま適用される。

### 実行順

**請求先 → 部署 → 委託先 → 案件**。案件は前段で登録した結果のIDマップ（名前→ID）を使って `client_id` / `department_id` / `contractor_id` を解決する。既存DBに登録済みの取引先も同じマップに含める。

### 既定値

| 列 | 値 |
|---|---|
| `unit_type` | `'quantity'` |
| `status` | `'accepted'` |
| `driver_visible` | `true` |
| `default_margin_rate` | DB既定値（10.00）に委ねる |

### 挿入経路

案件の挿入は既存の `createProject`（`web/src/app/admin/projects/actions.ts`）を経由する。`tenant_id` の付与をそちらが行っているため、ここでDBに直接挿入しない（取引先側で口座の暗号化を既存アクションに委ねているのと同じ方針）。

## 7. エラー処理

### 検証エラー

1件も登録せず、既存のエラー表（シート・行・列・理由）に案件シートの行も混ぜて表示する。

### 挿入中のエラー

Supabase の Server Action ではトランザクションを張れないため、挿入途中の失敗は既存の `partialFailure` と同じ扱いとする。「ここまでに登録した件数（請求先◯件・部署◯件・委託先◯件・案件◯件）」を表示し、残りだけのファイルで再実行するよう案内する。再実行時は重複検査が防波堤になる。

## 8. テスト方針

### 単体テスト（`web/src/utils/partner-import.test.ts` に追加）

- 正常系: 案件3行が変換され、`client_id` 解決用の名前・単価・既定値が期待どおり
- 必須欠落: 荷主・案件名・売上単価それぞれの空欄
- 数値: 全角数字・カンマ区切りの許容、負数・文字混入のエラー
- 参照解決: ファイル内の請求先で解決／既存DBの請求先で解決／どちらにも無い
- 部署の要否: 「あり」で空欄→エラー、「なし」で記入→エラー、「あり」で正しく記入→通る
- 重複: ファイル内重複、既存DB重複、部署違いの同名は通る
- 表記ゆれ: 全角空白・半角空白・全角英数字の違いが重複として検出される
- 採番: 既存最大値の次から連番、既存ゼロなら `P0001`
- ガイド行・記入例行のスキップ
- 後方互換: 案件シートが無いファイル、案件シートだけのファイル

### 画面確認

ローカルの dev サーバーで、テンプレDL → 記入 → プレビュー（件数表示） → 投入 → 再投入（重複で全件中止）を実測する。投入後はDBで `project_code` の採番と各IDの紐づきを確認する。
