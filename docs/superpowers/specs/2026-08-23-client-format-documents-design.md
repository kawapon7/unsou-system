# 導入先ごとの帳票様式（請求書・支払明細書）再現機能 要件定義

作成日: 2026-08-23
ステータス: **要件合意済み・実物様式の入手待ち・実装計画は未作成**
関連: `docs/superpowers/specs/2026-07-29-client-departments-design.md`（荷主の部署分割）、`docs/research/2026-08-22-owner-driver-tax-treatment.md`（支払通知書の法的位置づけ）

---

## 1. 背景と目的

HIBIKI は既に請求書（自社→荷主）と支払通知書（自社→委託先）の PDF を出せるが、レイアウトは HIBIKI 標準の1種類のみ。
実際の運送会社は「自社で使い慣れた様式」「荷主から指定された様式」を持っており、標準様式では現場に受け入れられない。

**目的**: 導入先（テナント）ごとに、その会社の実物と同じ見た目の請求書・支払明細書を PDF と Excel の両方で出せるようにする。1社目はおおば運送の実物様式。

## 2. 合意事項（2026-08-23 ボス決定）

1. **PDF と Excel の両方を既定で出す。** Google スプレッドシート利用者は Excel（.xlsx）経由で対応する（雛形は「ダウンロード→Excel形式」で預かり、出力した .xlsx はドライブにアップすればスプレッドシートで開ける）。スプレッドシートへの直接書き込み（Google API 連携）は初期スコープ外
2. **様式は「導入先ごと」に加えて「荷主ごと」に持てる。** 荷主マスタに使用する請求書様式を設定でき、未設定なら導入先の標準様式を使う。支払明細書は通常1様式（必要なら同じ仕組みで増やせる）
3. **様式ごとに「束ね方・呼び名・含める/分ける」のルールを出力側で定義する。** DB の計算・集計は1本のまま変えない（見せ方だけを変える）
   - 束ね方: 日別／案件別／種類別／ドライバー別（組み合わせあり）
   - 呼び名: HIBIKI の項目名 → その会社の呼び名（例: 待機料→付帯作業費）
   - 含める/分ける: 経費を運賃に含めるか別行か、控除の表示位置
4. **印鑑（角印・代表者印）とロゴは会社設定に画像（PNG 推奨、JPEG 可）として登録し、各様式に印字する。** 画像は Supabase Storage に会社ごとに隔離し、Server Action 経由でのみ取得する
5. **最初におおば運送の実物1社分を作り、そこで共通部分を固める。** 最初から全パターンを作り込まない。雛形が独特で合わない会社には「標準様式」を使う逃げ道を残す

## 3. 実現方式

```
HIBIKI のデータ ─┬─→ 雛形 Excel の所定セルに値を流し込み → .xlsx ダウンロード（xlsx/ExcelJS）
                 └─→ 雛形と同じ見た目に組んだ HTML → PDF（既存の PrintModal＝ブラウザ印刷方式）
```

- **Excel → PDF の自動変換はできない**（Cloudflare Workers 上に Excel/LibreOffice が無い）。PDF の見た目は様式ごとに1回、開発者が雛形を見て HTML で組む。以後はデータが変わるだけ
- 既存の `InvoiceDocument.tsx` / `PaymentNoticeDocument.tsx` は「標準様式」としてそのまま残す（既存利用者に影響なし）
- 様式の切替キーは会社マスタ（導入先の標準様式）と荷主マスタ（荷主指定様式）に持つ。具体的な列名・テーブルは実装計画で決める
- Excel 雛形の合計数式は**原則消して値で埋める**（HIBIKI の計算と Excel の計算がずれる余地を作らない）

## 4. 法的要件（様式がどうであれ必ず満たす）

| 要件 | 内容 | 対応方針 |
|---|---|---|
| インボイス制度（適格請求書） | 登録番号（T+13桁）、税率ごとの対象額と消費税額、発行者名、取引日、相手先名 | 荷主指定様式に記載欄が無くても**欄外または別紙で補完**するルールを持たせる |
| 電子帳簿保存法 | 発行した請求書・支払明細の控えを電子保存し、日付・相手先・金額で検索できること | 発行した PDF/Excel を HIBIKI 内に保管する。**様式より先に必要な土台** |
| 仕入明細書（支払通知書）の相手方確認 | 消費税法30条9項3号。委託先が内容を確認した記録が要る | 既存の確認フローと連動（`2026-08-22-owner-driver-tax-treatment.md` §5） |

## 5. 運用要件

- **確定と再発行**: 発行済みの訂正は上書きせず「取消→再発行」で番号を変え履歴を残す。既存 `utils/invoice-lock.ts` の延長で設計
- **請求書番号の採番**: 会社ごとに規則が違う（年度-連番、荷主コード-連番など）。会社設定に持つ
- **端数処理**: 消費税の切捨て/四捨五入、単価×数量の端数。**荷主ごとに違う**ことがあるので様式の設定項目に含める（1円ずれると差し戻される）
- **締め日と支払サイト**: 支払期限欄を自動で出すために会社／荷主設定に持つ
- **送付方法**: 初期はダウンロードのみ。メール送付（Resend）は後回し。送るなら送信記録を `notification_logs` に残す
- **権限**: 発行は管理者（master）のみ。ドライバー（sub）は自分宛ての支払明細の閲覧のみ
- **様式の版管理**: 荷主が様式を改定しても、過去の請求書は発行当時の様式で再表示できるよう、発行済み帳票に「どの様式・どの版で出したか」を記録する
- **改ページ**: 明細が1ページに収まらない場合の「2ページ目の形」を雛形を預かる時点で確認する

## 6. 技術上の注意

- PDF はブラウザ印刷方式のため**閲覧端末のフォントに依存**する。荷主側で崩れる事例が出たらフォント埋め込み方式への切替を検討（初期スコープ外）
- Excel 出力は書式保持のため、セル書式を保ったまま値を書けるライブラリ（ExcelJS 等）の採用を実装計画で判断する（現状導入済みの `xlsx` は書式保持が弱い）
- 印影画像は悪用リスクがあるデータ。公開 URL にしない。テナント分離（RLS／Storage ポリシー）の対象に含める
- 検証は実データ（`ooba/`）を使わず、**様式ごとのダミーデータ**で行う仕組みを最初に用意する（既存方針の踏襲）

## 7. 優先順位（実装計画の段階分け）

1. **土台**: 発行控えの保存・番号採番・確定/再発行（法的要件と整合）
2. **1社目**: おおば運送の実物様式（請求書・支払明細書）を PDF + Excel で
3. **拡張**: 荷主別様式の切替、印鑑・ロゴ画像、端数・締め日の設定化
4. **後回し可**: メール送付、フォント埋め込み PDF、スプレッドシート直接書き込み

## 8. 様式を1つ追加するときの手順（導入時の標準作業）

1. 雛形を預かる: Excel（.xlsx）、またはスプレッドシートを .xlsx で書き出したもの。印字済みの見本（PDF/紙の写真）も併せて
2. 確認事項を聞き取る: 束ね方（§2-3）、呼び名、経費・控除の扱い、端数処理、採番規則、締め日・支払サイト、2ページ目の形、印鑑・ロゴの画像
3. Excel 側: どのセルに何を入れるかの対応（セルマッピング）を定義する。合計数式は消して値で埋める
4. PDF 側: 雛形と同じ見た目の HTML コンポーネントを作る
5. ダミーデータで両方を出し、見本と突き合わせる（金額・行数・改ページ・印影位置）
6. 会社設定（または荷主設定）で様式を選び、本番で1枚出して相手先に確認してもらう

目安工数: Excel マッピング 1〜2時間、PDF 半日、確認込みで1様式1日。
