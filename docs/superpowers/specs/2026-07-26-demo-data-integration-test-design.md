# デモデータ総合テスト 設計書

- 作成日: 2026-07-26
- 目的: HIBIKI の各画面を実運用に近いデータで満たし、ボスが UI を触って動作・使い勝手・不具合を確認できる「興行データ」を用意する
- 種別: テスト用データ投入（プロダクトコードの変更なし）

## 1. 前提として確認した事実

調査で判明した事実。設計判断の根拠。

| 事実 | 内容 |
|---|---|
| Supabase プロジェクトは 1 つだけ | `unsou-system` (`hbpnhbsmsuhjyrohpluu`)。`web/.env.local` も本番 Cloudflare Workers も同じ DB を参照する。つまり**デモデータ投入＝本番 DB への投入** |

| 既存 seed スクリプトの期間は 6 月固定 | `seed-activity-data.mjs` は 2026-06-01〜15。今日（7/26）にカレンダーを開いても空に見える |

## 2. 決定事項

| 論点 | 決定 | 理由 |
|---|---|---|
| 投入先 | 本番 DB に印付きで投入し、テスト後に印限定で削除 | 実データが無くリスクが低い。かつ本番環境そのもの（Workers・Resend 含む）を検証できる唯一の方法 |
| テストの目的 | ボスが UI を触るための興行データ | 画面がスカスカでは使い勝手も不具合も見えない |
| 期間・規模 | 2026 年 6 月（締め済み）＋ 7 月（稼働中）の 2 か月 | 「先月はどうだったか」と「今何が起きているか」の両方が UI で確認できる。業績サマリーの前月比も見える |
| 既存ダミーデータ | 一旦削除して作り直す | 現状は「石原裕次郎」「聖徳太子」等の場当たり的な名前で単価ルールも揃っておらず、興行データとして雑然として見える |
| 実装方式 | 既存ロジックを土台に統合スクリプト 1 本を新規作成 | 既存 9 本の逐次実行では日付が噛み合わない。SQL 直接投入は口座暗号化が `crypto.ts`（Node 側）依存のため規約違反 |

### 3-1. `web/scripts/seed-demo-full.mjs`（投入）

### 3-2. `web/scripts/clear-demo-data.mjs`（削除）

- 既定は **DRY RUN**。対象件数をテーブルごとに表示するだけで、何も削除しない
- `--execute` を明示的に付けたときだけ実際に削除する
- 保護リスト（`kawapon7+driver@gmail.com` の委託先）をコード内に定数で固定。対象から機械的に除外する
- `approval_history` / `notification_logs` には**一切触れない**（不変ログ・UPDATE/DELETE 全ロール禁止、CLAUDE.md §2）

## 5. 安全策

CLAUDE.md §2 および HANDOVER §2-6S に基づく。

1. 既存ダミーデータの削除は**印付き限定**。件数を表示してから 1 コマンドずつ承認を取って実行する（本番 DB への変更は一括で進めない）
2. 口座情報は平文で DB に入れない。必ず `utils/crypto.ts` の AES-256-GCM 相当のロジックを通す
3. `approval_history` / `notification_logs` は INSERT のみ。UPDATE / DELETE は投入・削除の両スクリプトで一切発行しない
4. DB アクセスはサービスロール経由。`anon` ロールでの直接アクセスはしない
5. コミット時は 3 ステップ（`git status` 目視 → シークレット漏れ grep → ファイル明示 add）を通す

## 6. 付随して発見した課題（本作業のスコープ外）

`driver_project_assignments.tenant_id` のみ型が `uuid`。他テーブルは全て `text`（値は `'local-dev'`）。
現在このテーブルは空のため無害だが、**テナント分離 F0 実装時に必ず衝突する**。F0 の計画に反映すること。
