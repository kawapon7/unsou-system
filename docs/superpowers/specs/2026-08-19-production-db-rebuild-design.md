- 作成日: 2026-08-19

- 関連: `docs/HANDOVER_MASTER.md` §5-2「本番DBの作り直し（現行をテスト環境化）」、`docs/superpowers/plans/2026-07-27-tenant-isolation-phase0.md`

## 1. 背景

現行の本番DB（`hbpnhbsmsuhjyrohpluu` / `unsou-system`）はテストも開発も兼ねており、デモデータで汚染されている。実データ未投入の今なら移行コストがほぼゼロのため、**現行をテスト環境として残し、新しいSupabaseプロジェクトを本番として新規作成する**方針が2026-07-27に決定された。

前提条件である「マイグレーションを流せば本番スキーマが再現できる状態」は2026-08-19に完全充足した（F0の5本のファイル名をDB採番へ合わせ、ローカル56件 = `schema_migrations` 56件の1:1一致を機械照合で確認）。

### 現況（2026-08-19時点・読み取り確認済み）

- 組織: `kawapon7's Org`（`rqbecemvrxollkppfrwb`）1つのみ
- プロジェクト: `unsou-system` 1つのみ（region `ap-northeast-1` / PostgreSQL 17.6.1.127）
- 新規プロジェクト作成コスト: **月額 $0**（API照会で確認）
- マイグレーション: 56本（ローカル・DB一致）

## 2. スコープ

### やる

1. 新組織の作成（ボスがダッシュボードで手作業）
2. 新組織内に新プロジェクトを作成
3. マイグレーション56本を適用
4. 現行DBとのスキーマ機械照合（完了条件）

### やらない（別セッション）

- 切替（`NEXT_PUBLIC_SUPABASE_URL`・anonキー・GitHub secrets更新・再デプロイ）
- A社実マスタの投入
- 認証ユーザーの作成

新DBは完成後も**どこからも参照されない状態で待機**する。本番URL（`https://unsou-system.hibiki-app.workers.dev`）は現行DBを向いたままのため、A社へのデモ環境は壊れない。

## 3. 決定事項

### 3-1. 手順③「ダミーデータ一掃」を工程から削除する

従来の工程は「③ダミーデータ一掃 → ④本番DB新規作成＋クリーン投入 → ⑤実運用開始」だったが、③は不要かつ有害と判断し削除する。

| 理由 | 内容 |
|---|---|
| 不要 | 新DBはマイグレーションから**空で生成**される。ダミーは最初から入らない |
| 有害 | 現行DBは**テスト環境として残す**方針。そこのダミーは汚れではなくテスト資産であり、消すとテスト環境が空になる |
| 実行不能 | `approval_history` / `notification_logs` は全ロールで DELETE 禁止（不変ログ）。物理的に消せない |

③の位置に入る**本当の作業は「A社実マスタの収集」**（自社情報・荷主・委託先・案件・単価ルール）。2026-08-19時点で「まだ無い／これから聞く」状態であり、**ボスがA社に確認する他人待ちタスク**。これが実運用開始のクリティカルパスの最長経路になる。

### 3-2. 適用手段は Supabase CLI の `db push`。MCP の `apply_migration` は使わない

**本設計で最も重要な決定。**

MCP の `apply_migration` は `schema_migrations` の version を**自動採番する**ため、ファイル名の version がそのまま記録されない。これは2026-08-19に是正したばかりのズレ（F0の5本）を生んだ原因そのものであり、新DBで同じことを繰り返せば「マイグレーション = 本番スキーマ」という本計画全体の前提が初日から崩れる。

CLI の `supabase db push` はファイル名の version をそのまま `schema_migrations` に記録するため、56本が名前どおりに入る。CLI は動作確認済み（v2.115.0、`npx supabase` で実行可能）。

⚠️ `db push` は DBパスワードを要求する。**ボスが入力すること**（値を会話・ログ・ファイルに残さない）。

### 3-3. テナント行の追加seedは不要

`20260805113852_create_tenants.sql` が A社行を自ら投入する。

```sql
INSERT INTO public.tenants (id, name)
VALUES ('00000000-0000-0000-0000-0000000000a1', 'A社')
ON CONFLICT (id) DO NOTHING;
```

正準テナントUUIDは現行DBと同一（`00000000-0000-0000-0000-0000000000a1`）になる。将来この2つのDBのデータを突き合わせる場面で `tenant_id` が一致するため、同一にしておくほうが扱いやすい。**新規採番はしない。**

### 3-4. 新組織に作る（現組織に2つ目を作らない）

Supabaseのプランは**組織単位**の課金であるため、本番だけを Pro 化するには組織を分ける必要がある。Pro の日次バックアップ7日分は、A社の実データが入った後には実質必須。Free のバックアップ手段は `supabase db dump` のみ。

現組織に2つ目を作る案は、将来 Pro 化した際にテスト用の現行DBまで課金対象に巻き込むため採らない。ただしプロジェクトの組織間移動は公式機能として存在するため、この判断は不可逆ではない。

⚠️ **Supabase MCP に組織作成のAPIは無い。** 新組織の作成はボスがダッシュボードで手作業する。作成後、MCPトークンが新組織を参照できるかは未確認であり、参照できない場合はプロジェクト作成もダッシュボード手作業になる。

## 4. 新プロジェクトの構成

| 項目 | 値 | 根拠 |
|---|---|---|
| 組織 | 新規作成。名称は `hibiki-production-org`（ボスから別案が出なければこれ） | 3-4 |
| プロジェクト名 | `hibiki-production` | 現行の `unsou-system` と役割で区別する。ボスから別案が出なければこの名前で作る |
| リージョン | `ap-northeast-1`（東京） | 現行と同一。A社は国内利用 |
| プラン | Free で作成し、実運用開始前に Pro へ | 実データ投入までバックアップ要件が発生しない |
| PostgreSQL | 選べるなら現行と同メジャー（17系） | スキーマ再現の同一性を保つ。⚠️新規作成時にバージョンを選べずデフォルトが18系以降になる場合は、それを受け入れたうえで §5 の機械照合に差分が出ないことで妥当性を判定する（差分が出たら切替に進まない） |

## 5. 完了条件（機械照合）

2026-07-27に416オブジェクトを突合したのと同じ手法で、現行DBと新DBを照合する。

1. **`schema_migrations` が56件**、ローカルのファイル名 version と1:1一致
2. **スキーマオブジェクトの名前と件数が完全一致** — 列 / 制約 / 索引 / RLSポリシー / トリガー / 関数。それぞれソート済みリストを取得し `diff` で差分ゼロを確認
3. **不変トリガーが有効**（`approval_history` / `notification_logs` の UPDATE・DELETE 拒否 4本）
4. **`tenants` に A社1行**、`tenant_id` 系のFK18本が張られている

差分が1件でも出た場合、それは「マイグレーションで本番スキーマを再現できていない」ことを意味する。**切替へ進まず原因を特定して潰す。** ここは本計画全体の前提そのものであり、妥協しない。

⚠️ 現行DBと新DBでは**行数は一致しない**（新DBは `tenants` 1行のみ）。照合対象はスキーマであってデータではない。

## 6. リスクと安全策

| リスク | 安全策 |
|---|---|
| 現行の本番DBを壊す | **一切書き込まない。** 照合は読み取り専用クエリのみ |
| DBパスワードの露出 | `db push` のパスワードはボスが入力。会話・ログ・ファイルに残さない |
| 新DBに誤って切替が走る | 今回は `.env` / GitHub secrets / `wrangler.toml` を**一切触らない**。切替は別セッションの別作業 |
| MCPトークンが新組織を見えない | 見えない場合はダッシュボード手作業に切り替える（手順を提示する） |
| マイグレーション適用の失敗 | 新DBは空なので、失敗したらプロジェクトごと削除して作り直せる（$0・不可逆でない） |

## 7. この設計が完了した後に残るもの

実運用開始（⑤）までの残作業。本設計の範囲外。

1. **A社実マスタの収集**（他人待ち・クリティカルパス最長）
2. 新DBへの実マスタ投入（投入手段は実データの形が分かってから設計する）
3. 認証ユーザーの作成（現行の9ユーザーは移行せず、A社の実ユーザーを新規作成）
4. 切替（`NEXT_PUBLIC_SUPABASE_URL`・anonキー・GitHub secrets・再デプロイ・動作確認）
5. 本番プロジェクトの Pro 化
