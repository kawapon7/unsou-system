# 取引先一括インポート（運営者専用）設計書

日付: 2026-08-24 ／ ステータス: ボス承認済み（会話内で案A承認）

## 目的

初期導入時の取引先登録（委託先・請求先・部署）を、配布した記入用Excelテンプレートから一括投入できるようにする。
**運営者（HIBIKI側＝ボス）専用機能**とし、クライアント側の管理者には存在自体を見せない。
初期データ移行を「HIBIKIのサービス」として提供する商品設計を権限の壁で守る。

## 決定事項（ボス確認済み）

| 論点 | 決定 |
|---|---|
| 対象データ | 委託先（contractors）・請求先（clients）・部署（client_departments）の3種すべて |
| ファイル形式 | Excel（.xlsx）1ファイル・3シート構成 |
| 重複時の挙動 | **全件中止**。既存と同名（または同メール）が1件でもあれば何も登録せずエラー一覧を表示 |
| 解析場所 | **案A: ブラウザ側で解析**（SheetJS）。Server ActionにはJSONのみ送る |
| 権限 | 運営者ゲート新設（環境変数のUUID允許リスト）。正式な `operator` ロール化はB社前のRLS見直し時に実施 |

## アーキテクチャ

```
[運営者ブラウザ]
  Excelファイル選択
  → SheetJSで3シートをJSON化（クライアント側）
  → プレビュー表示（エラー行は赤・エラーゼロまで投入ボタン無効）
  → Server Action呼び出し（JSONのみ・ファイルは送らない）

[Server Action]（検証の正本はこちら）
  1. 運営者ゲート: 実行者UUID ∈ OPERATOR_USER_IDS（環境変数）でなければ拒否（fail-closed）
  2. 全行を再検証（必須・形式・列挙値・親子解決）
  3. 重複検査（既存clients/contractorsとの同名・同メール照合、ファイル内重複も検査）
  4. 1件でも問題があれば全件中止（挿入前に検出するため部分投入は発生しない）
  5. 問題ゼロなら投入: 既存の登録経路と同じ処理を通す
     - encryptBankFields で口座4項目（bank_name/bank_branch/account_number/account_holder）を暗号化
     - tenant_id 付与（getCurrentTenantId）
     - 部署は「請求先名」で親clientsを解決してclient_idを設定
  6. 結果報告: 種別ごとの登録件数
```

### 投入順序と親子解決

1. 請求先（clients）→ 2. 部署（client_departments、親は同ファイル内の請求先名で解決）→ 3. 委託先（contractors）。
部署シートの請求先名がファイル内にも既存DBにも見つからない場合は検証エラー（全件中止）。
委託先の `parent_contractor_id`（2次委託）は初期投入では対象外（空欄固定）。投入後に画面から設定する。

## 運営者ゲート

- 環境変数 `OPERATOR_USER_IDS`（カンマ区切りUUID）。当面はボスの本番アカウントUUID 1件。
- 検査箇所は**2箇所**: ①インポートページ（Server Component側で非該当なら404相当）②Server Action冒頭（非該当なら即エラー）。UIメニューにも非該当者には項目を出さないが、これは利便性であって防御はサーバー側検査。
- 未設定（環境変数が空/不在）の場合は**全員拒否**（fail-closed）。
- 将来: B社前のRLS見直しで正式ロール `operator` に昇格。本設計はその移行を妨げない（ゲート関数を1つに集約しておく）。

## Excelテンプレート仕様

1ファイル3シート。各シート1行目=項目名（日本語）、2行目=記入例。記入例の各セルは「例）」で始める書式とし、**取込時は先頭セルが「例）」で始まる行を自動スキップ**する（消し忘れによる誤登録を防ぐ）。

## 検証ルール（純関数に切り出し・ユニットテスト対象）

- 必須列の空欄検出（行番号つき）
- 列挙値の不一致（「翌月」を「よく月」等）
- メール形式・登録番号形式（T+13桁）・口座番号の桁
- ファイル内重複（同名・同メール）
- 既存DBとの重複（同名 or 同メール → 全件中止）
- 部署の親（請求先名）解決失敗
- 委託先メールの重複は特に厳格に（contractors.email はNOT NULLかつアカウント紐づけに使われるため）

エラーは全件まとめて返す（1件目で止めない）。プレビュー画面に行番号・列名・理由を一覧表示。

## 画面

- パス: `/admin/ops/import`（運営者ゲート内）。ナビへの追加は運営者判定時のみ表示。
- 構成: ①ファイル選択 ②シートごとのプレビュー表（正常=白、エラー=赤+理由）③集計（登録予定n件・エラーn件）④投入ボタン（エラー0のときのみ活性）⑤結果表示。
- スタイルは既存の管理画面規約（`CATEGORY_STYLES` 経由）に従う。

## エラー処理・安全設計

- 投入は「全行の検証が通ってから挿入開始」のため、途中失敗による部分投入は原理上起きにくいが、挿入中のDBエラー（ユニーク制約等）が起きた場合は**その時点で中断し、何件目まで入ったかを明示**する。トランザクション化はSupabase Server Action経由では不可のため、再実行時は重複検査が防波堤になる（既に入った分は同名検出で全件中止→残件だけのファイルを作り直す運用）。この制約は結果画面に明記する。
- 口座情報はブラウザ→サーバー間もHTTPS、DBへは必ず `encryptBankFields` 経由。**平文で保存される経路を作らない**。
- インポート実行の事実は結果として画面表示するのみ（approval_history への記録は書類系ではないため対象外）。

## テスト

- 検証純関数のユニットテスト（正常系・各エラー系・境界値: 締め日28、T番号桁、列挙値ゆれ）
- 運営者ゲートのユニットテスト（允許/拒否/環境変数未設定=拒否）
- 結合確認: テスト環境（旧DB）でテンプレ実ファイルを投入→画面で復号表示・DB上は暗号文であることを照合
