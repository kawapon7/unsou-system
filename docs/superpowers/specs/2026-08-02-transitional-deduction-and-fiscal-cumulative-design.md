# 経過措置の差し引き一本化と、委託先ごとの年度累計表示 — 設計書

作成: 2026-08-02 ／ 状態: 設計確定・実装前

## 1. 何を作るか（要約）

2部構成。独立して進められる。

- **第1部**: 支払通知書の経過措置差し引きを、率の正本 `utils/transitional-deduction.ts` に一本化する。実害のある誤りが3つあり、これを直す
- **第2部**: 委託先ごとに「この事業年度いくら払ったか」を表示する。1億円の上限判定そのものは**作らない**

## 2. 背景

2026-08-02 に経過措置の率を令和8年度改正へ追随させ、3ファイルの重複を `utils/transitional-deduction.ts` に統合した（コミット `76b2cb8`）。
しかしその後、**4本目の重複**が見つかった。`admin/billing/actions.ts` の `calcDeductionRate` で、名前が違うため当初の調査で拾えていなかった。
これが**実際に支払通知書を生成している経路**である。

## 3. 一次資料で確認した事実

⚠️ 以下は国税庁の一次資料で裏取り済み。実装判断はここに基づく。

### 3-1. 経過措置の期間と割合（インボイスQ&A 問113【令和8年4月改訂】）

| 期間 | 控除できる割合 |
|---|---|
| 令和5年10月1日〜令和8年9月30日 | 仕入税額相当額の 80% |
| 令和8年10月1日〜令和10年9月30日 | 70% |
| 令和10年10月1日〜令和12年9月30日 | 50% |
| 令和12年10月1日〜令和13年9月30日 | 30% |

✅ **`utils/transitional-deduction.ts` の実装と完全一致を確認済み**（2026-08-02）。

### 3-2. 上限は「委託先1社ごと」（問113 注記）

注記に「一の免税事業者等から行う」と明記。**取引相手1社ごとに判定する**。全社合計ではない。
金額は課税期間の開始日で切り替わる。

| 課税期間の開始 | 上限（税込） |
|---|---|
| 令和6年10月1日〜令和8年9月30日に開始 | 10億円 |
| 令和8年10月1日以後に開始 | 1億円 |

⚠️ **調査中に取得した要約の1つが「全体の合計」と誤って解釈していた。** その要約自身が引用した原文と矛盾していたため、原文を優先した。**要約を信用せず原文にあたること。**

### 3-3. 立替金は委託先への対価に含まれる

質疑応答事例「実費弁償金の課税」（令和7年8月1日現在・消基通10-1-4）。
弁護士が受け取る実費弁償の交通費は、交通機関等への支払が「実質的に依頼者による直接払と認められるもの」でない限り、報酬に含まれ課税対象になる、とされている。

**HIBIKI の構図**: 受託元 → クライアント(A社) → 委託先。高速代は**委託先が自分のETCカードで支払い**、A社が精算している。
領収書はETCカード所有者＝委託先名義。したがって高速道路会社への支払いはA社による直接払ではない。
→ **委託先への対価（運送料）に含まれる＝A社から見て委託先からの課税仕入れ**、と読める。

問94（立替金）とも整合する。立替金として扱えるのは、その課税仕入れが**A社自身のもの**であることを立替金精算書等で明らかにできる場合に限られる。ETCカードが委託先名義である以上、この構図には当てはまらない。

⚠️ **派生する重大な論点**: 問113 の経過措置は「免税事業者等からの**課税仕入れ**」全般が対象。
立替金も課税仕入れなら**そこにも経過措置がかかる**。現行システムは労務報酬にしかかけていないため、**差し引き不足＝支払超過**の可能性がある。
**これは支払額が変わる変更なので、税理士確認が取れるまで実装しない**（第5章に記録）。

## 4. 設計

### 4-1. 第1部: 差し引き計算の一本化

**廃止するもの**: `admin/billing/actions.ts` の `calcDeductionRate`

現行の3つの誤り:

| | 実物の支払明細書・他3実装 | `calcDeductionRate`（実稼働中） |
|---|---|---|
| 基準額 | **税込**額 × 率 | 税抜額 × 率（`laborTax × 0.2`） |
| 2026年10月以降 | 3% | 0.5（＝5%相当）のまま |
| 2029年10月以降 | 10% | **0（差し引き無し）** ← 向きが逆 |

**変更内容**:

- 率は `utils/transitional-deduction.ts` の `getDeductionRate(date, isRegistered)` を使う
- 基準額を**税込**にする: `Math.round((labor_tax_excluded + labor_tax) * rate)`
  - ⚠️ 端数処理を現行の `Math.floor` から `Math.round` へ変更する。実物の明細書と一致が確認されているのは `taxCalculator.ts` の `Math.round` 式であるため（HANDOVER §5-4 2026-07-31 C節）。差は最大1円
- `isRegistered` の判定は現行を踏襲: `contractor.invoice_registration_type === '適格'`
- 修正箇所は2つ:
  - `fetchPaymentByContractor`（一覧表示）
  - `generatePaymentNotice`（支払通知書の生成・DB書き込み）

**確定済みの支払通知書は書き換えない。** 実際に支払った記録であり、遡って変えるほうが事故になる。次に確定する月から新基準が適用される。

#### ⚠️ 率は「稼働日ごと」に判定する（月単位ではない）

**消費税法基本通達 11-3-1（課税仕入れを行った日の意義）**: 課税仕入れを行った日とは、資産の譲受け・借受けをした日、又は**役務の提供を受けた日**をいう。
**支払日でも請求日でもない。** 運送役務なら実際に走った日＝`work_records.work_date`。立替金なら `expense_records.expense_date`。

現行実装は対象月（`yearMonth`）で率を1つ決めている。これは**近似ではなく誤り**であり、直す。

⏰ **最初に差が出るのは2026年9月21日〜10月20日の締め期間**（20日締めの委託先）。1枚の支払通知書の中に

- 9月21日〜9月30日の稼働 → 2%
- 10月1日〜10月20日の稼働 → 3%

が混在する。月単位で判定すると必ず間違える。**この期限があるため第1部に含める。**

**計算方法**:

1. 対象期間の `work_records` / `expense_records` を、稼働日（支出日）から求めた率で**グループ分け**する
2. 消費税額そのものは従来どおり、税抜合計に対して1回だけ四捨五入する（税率ごと1回のインボイス端数ルール）
3. 経過措置の差し引きは**率のグループごとに** `Math.round(税込小計 × 率)` を計算し、合算する

⚠️ グループごとの税込小計を足した額は、税抜合計＋四捨五入後の消費税額と数円ずれうる。差し引き額の算出にのみ使い、請求・支払の本体金額には使わないこと。

### 4-2. 第2部: 委託先ごとの年度累計表示

#### (a) 決算月の設定

- `companies` に `fiscal_year_end_month`（integer, NULL許容, 1〜12）を追加するマイグレーション
- 「マスタ・設定 → 自社情報」に決算月のセレクトを追加
- 事業年度 = 決算月の翌月1日 〜 決算月末日
- ⚠️ **未設定なら暦年（1月〜12月）で集計し、画面に「決算月が未設定のため暦年で集計しています」と表示する。** 未設定でPDF生成等を止めることはしない（fail-closed にするほどの実害がない）

#### (b) 事業年度の算出（新規モジュール）

`web/src/utils/fiscal-year.ts`
⚠️ `'use server'` を付けないこと（純粋関数を export するため）

```
fiscalYearRange(yearMonth: 'YYYY-MM', fiscalYearEndMonth: number | null): { from: 'YYYY-MM-DD'; to: 'YYYY-MM-DD' }
```

⚠️ 日付は `utils/closing-period.ts` と同じくローカル日付の文字列で組み立てる。`toISOString()` は使わない（JSTでは1日ずれる）。

#### (c) 累計の算出

委託先ごと・事業年度ごとに、**確定済みの支払通知書**を合算する。

- 確定済みの判定: `payment_notices.locked = true`（実データ上 `status='locked'` / `approval_status='approved'` と揃っている）
- 範囲: `notice_month` が事業年度内
- テナント条件（`tenant_id`）を必ず掛ける
- 3つの数字を出す:
  - 労務報酬（税込） = `labor_tax_excluded + labor_tax`
  - 立替金（税込） = `expense_tax_excluded + expense_tax`
  - 合計
- ⚠️ **表示している月が未確定でも、その月の計算中の額は加算しない**（2026-08-02 ボス判断で改訂）
  - 当初この設計書は「未確定の月の計算中の額を加算する」としていたが、**確定額と見込み額が
    1 つの数字に混ざる**と「この金額はもう動かないのか、まだ動くのか」が読めなくなる。
    支払いに関わる数字なので、動かない額であることを優先する
  - もともと累計は年間 1 億円の上限判定のために構想したが、その判定は「委託先 1 社で
    年 1 億円には届かない」という理由で**意図的に作っていない**（4-3 参照）。
    つまり現状の累計は参考表示であり、リアルタイム性を優先する理由が弱い
  - 画面には「確定済みの支払通知書のみを合計している」旨を明記する（実装済み）
  - 将来「見込みも知りたい」となった場合は、1 つの数字に混ぜず
    「年度累計（確定済み）」と「今月の集計中」を**2 つ並べて出す**こと

⚠️ **3列に分ける理由**: 立替金を課税仕入れに含めるかは税理士確認待ち。分けておけば結論がどちらでも画面を作り直さずに済む。

#### (d) 表示

- 場所: 「請求・支払管理(OUT)」の委託先ごとの行
- 記録が事業年度の途中から始まっている場合、累計の横に「（2026年7月からの記録）」と小さく添える
  - 判定: その事業年度内で最も古い確定済み `notice_month` が、事業年度の開始日より後
- ⚠️ 専用の警告アラートは出さない。上限判定を作らない以上、警告する対象がないため

### 4-3. 作らないもの（意図的に外す）

- 1億円／10億円の上限判定、および上限をまたぐ月の分割計算
- 8千万円などの閾値アラート
- 免税事業者への支払いの全社合計
- 立替金への経過措置適用（税理士確認待ち）

**理由**: 上限は**委託先1社ごと**の判定であり、導入予定先の年商（8千万円クラス）では、1社への年間支払いが1億円を超えることは起こらない。効かない条件のためのコードを今抱えない。累計が見えていれば、規模が伸びたときに気づける。

## 5. 税理士に確認する項目

⚠️ いずれも支払額・請求額に直結する。確認が取れるまで実装しない。

1. **立替金（高速代）の扱い** — 委託先が自分のETCカードで払った高速代をA社が精算している。領収書はETCカード所有者（委託先）名義。実費弁償金の質疑応答事例に照らすと委託先への対価に含まれ、経過措置の対象になると読めるが、その理解でよいか
2. **売上請求書から経過措置を外す（論点B）** — `finalizeInvoice` が取引相手の登録状況を見て差し引いている。制度上は買い手側の話であり、判定の主語が誤っていると考えられる
3. **差し引きの基準額を税込×率に変更すること** — 委託先への支払額が減る（税抜100万円の月で約2,000円）。委託先への説明が要るか

## 6. テスト

- `fiscal-year.ts`: 決算月3月・12月・未設定、年またぎ、うるう年
- 累計の集計範囲: 事業年度の境界、確定済みのみを数えること、テナント分離
- 第1部: 率と基準額（税込）、`Math.round` の端数、登録事業者なら0
- **⚠️ 稼働日ごとの率判定**: 2026年9月21日〜10月20日の締め期間で、2%分と3%分が正しく分かれて合算されること（月単位判定なら落ちるテストにする）
- ⚠️ 既存の `transitional-deduction.test.ts` が持つ「旧実装が正本と一致すること」のガードに、`calcDeductionRate` 廃止後の経路も含める
