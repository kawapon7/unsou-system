# ドライバーアプリ 機能拡充 設計書

- 作成日: 2026-08-17
- 状態: 設計確定（ボス承認済み）
- 背景: ドライバー画面が入力専用になっており、自分の報酬・実績・過去分を確認する手段が無い。
  「この水準では料金をいただけない」というボス判断により、確認系機能をまとめて実装する。

---

## 1. 現状と欠落

仕様 §2-4-2 は6画面を定義しているが、実装されているのは3つだけ。

| 仕様 §2-4-2 | 実装状況 |
|---|---|
| ①今日の記録 | ✅ `/driver/schedule`（カレンダーから登録・完了報告） |
| ②立替金の入力 | △ 入力はあるが履歴は `/driver/billing` に分離 |
| ③今月の実績（稼働日数・総稼働時間・支払予定額） | ❌ 無し |
| ④今月の明細（日付／案件／数量／金額の全件） | ❌ 無し |
| ⑤支払通知書の確認・承認 | ✅ `/driver/billing` |
| ⑥支払い明細PDF | △ 通知書がある月しか開けない |

加えて下部ナビの「マイページ」はリンクの無い飾り（`/driver/dashboard` はナビから辿れない）。

## 2. 決定事項（ボス判断）

| 論点 | 決定 |
|---|---|
| 進行中の月の金額 | **ライブで見せる**。ただし「見込み」と明示する |
| 画面構成 | **ホームを新設して4タブ**（ホーム／予定・実績／支払／マイページ） |
| 過去分の保持期間 | **上限を設けない**（確定申告・税務調査で最大7年遡るため。データ量は1人あたり月1行で問題にならない） |
| 年の区切り | **暦年**（確定申告に合わせる。締め日ベースにしない） |
| PDFの保存 | **都度生成のまま**。承認時に「確定申告用に保存してください」と促す |
| 追加機能 | ①確定申告用の年間サマリー ②単価の内訳表示 ④アプリ内お知らせ |
| 見送り | ③立替金のレシート写真（Supabase Storage の導入判断が別途必要） |
| やらない | 運転日報・アルコールチェック（法令記録の責任を負うため）、GPS追跡（監視色・雇用性の論点）、車検/免許期限管理（自社車両向けで委託先には価値が薄い） |

## 3. 画面構成

```
🏠 ホーム    📅 予定・実績    📄 支払    👤 マイページ
```

| タブ | 役割 | 対象期間 |
|---|---|---|
| ホーム | 今月の見込み金額・稼働日数・個数／未承認バッジ／直近の予定 | 当月 |
| 予定・実績 | 既存カレンダー ＋ 予定リスト（今日以降）＋ 実績リスト（月切替） | 月単位 |
| 支払 | 未承認の確認・承認 ＋ 年別の支払履歴 ＋ 年間サマリー ＋ 明細PDF | 全期間 |
| マイページ | 氏名・メール・インボイス区分・ログアウト | — |

### 3-1. ホーム（新規 `/driver/home`）

- 今月の見込み金額（最大サイズ）＋「※ 確定前の見込みです」
- 稼働日数／個数
- 未承認の支払通知書があれば警告行（タップで支払タブへ）
- 直近の予定3件

### 3-2. 予定・実績（既存 `/driver/schedule` を拡張）

上部にセグメント切替 `[カレンダー] [予定] [実績]` を置く。**既存カレンダーの実装は変更しない**（動いているものを壊さない）。

- 予定リスト: 今日以降を日付順。案件名・時間帯
- 実績リスト: 月切替つき。1行＝日付／案件名／数量／金額。末尾に月合計。立替金も同じ月の下に並べる
- 実績行をタップ → **単価の内訳**（例: 380個 × ¥85 = ¥32,300）を展開

### 3-3. 支払（既存 `/driver/billing` を拡張）

- 未承認カード（現状維持）
- 年セレクタ `2026年 ▾` → 月別リスト（月・金額・状態・PDFボタン）
- **年間サマリー**: 報酬合計・立替経費合計・経過措置控除合計・運送保険合計・差引支給合計
- 年の選択肢は「そのドライバーに通知書が存在する年」だけ出す
- PDFモーダルに「確定申告用に保存してください」の一文

### 3-4. マイページ（新規 `/driver/profile`）

氏名・メール・インボイス区分（登録/免税）・ログアウト。現在ナビにあるだけで中身が無い状態を解消する。

## 4. スマホ視認性の原則（全画面共通）

屋外・片手操作・老眼を想定する。

- 本文16px下限。**金額は28〜32pxの太字**。ラベルは小さく、数字を大きく
- 1行1情報。表を横に伸ばさない（横スクロールは事故のもと）
- タップ領域44px以上。主要ボタンは横幅いっぱい
- 色に頼らない。承認済/未承認は文字とアイコンでも区別する

## 5. データ設計

### 5-1. 新規 Server Actions（`_actions/driver-actions.ts` に集約）

| アクション | 用途 | 備考 |
|---|---|---|
| `fetchMyMonthSummary(yearMonth)` | ホームの見込み金額・稼働日数・数量 | 金額は `computePaymentNoticeAmounts` に委譲 |
| `fetchMyWorkRecords(yearMonth)` | 実績リスト（単価内訳込み） | `calcWorkAmount` の計算根拠も返す |
| `fetchMyUpcomingSchedules(limit)` | 直近の予定 | 今日以降のみ |
| `fetchMyPaymentHistory(year)` | 年別リスト＋年間合計 | **既存の `limit 12` を廃止** |
| `fetchMyAvailableYears()` | 年セレクタの選択肢 | 通知書が存在する年のみ |
| `fetchMyNotifications()` / `markNotificationRead(id)` | お知らせ | 下記 5-3 の制約あり |

### 5-2. 金額の正本

金額は例外なく `utils/payment-notice-calc.ts` の `computePaymentNoticeAmounts` を通す。

⚠️ **ドライバー画面用に別計算を書かないこと。** 2026-08-10 に一覧が独自計算（暦月固定）を持っていたために親分の一覧とPDFで金額が食い違う事故が起きている。同じ型を繰り返さない。

確定通知書がある月は保存値、無い月はライブ計算という既存の切り替えをそのまま使う。

### 5-3. お知らせの既読管理（新テーブル）

`notification_logs` は**不変ログ（INSERTのみ・UPDATE/DELETE 全ロール禁止）**のため、既読フラグをこの表に持てない。規約を曲げず、別テーブルを新設する。

```sql
-- migrations: notification_reads
create table public.notification_reads (
  id              uuid primary key default gen_random_uuid(),
  tenant_id       uuid not null references public.tenants(id),
  notification_id uuid not null references public.notification_logs(id),
  contractor_id   uuid not null references public.contractors(id),
  read_at         timestamptz not null default now(),
  unique (notification_id, contractor_id)
);
```

⚠️ **本番への適用はボスの承認を得てから、SQL Editor で1本ずつ実行する。** 適用後に `supabase_migrations.schema_migrations` へ記録し1:1一致を維持する。

### 5-4. ファイル配置の是正

現在ドライバー向けの読み取りが3ファイルに散っている（`dashboard/actions.ts` / `_actions/driver-actions.ts` / `_actions/scheduleActions.ts`）。

2026-08-17 のPDF認可バグは、この分散により同じ委託先ID解決が3箇所に増殖したことが原因だった。**読み取りは `_actions/driver-actions.ts` に寄せ**、`dashboard/actions.ts` には書き込み系（立替金申請・完了報告）だけを残す。

## 6. エラー処理

- 認可は `utils/auth.ts` の `resolveContractorId` を全アクションで使う。解決不能なら fail-closed
- **金額の取得失敗時に0円を表示しない。** 「取得できませんでした」と出す。0円表示は「稼働したのに報酬0」と読めるため、報酬画面では最悪の誤表示になる
- 「見込み」と「確定」を必ず文字で区別する。混ぜると、後から金額が動いたときに不信を招く

## 7. テスト方針

- 集計ロジック（年間サマリー・月次サマリー・単価内訳）は**純関数に切り出して vitest**。DBクライアントは薄いインターフェースで偽装する（`resolveContractorId` と同じ形）
- `utils/phantom-columns.test.ts` が存在しない列の参照をソース全走査するため、新規クエリも自動的にこの網に乗る
- 画面確認はドライバーアカウント（`driver01@example.com` = 石原裕次郎、`kawapon7+driver@gmail.com` = 鈴木次郎）で行う

## 8. スコープ外（記録）

- 立替金のレシート写真（Supabase Storage の導入・保存コスト・削除規則の設計が必要）
- 支払通知書PDFの確定版保存（同上）
- 運転日報・アルコールチェック・GPS追跡・車検/免許期限管理（2章の理由により意図的に不採用）
